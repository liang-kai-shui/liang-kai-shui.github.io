看板娘能聊天了，然后后台一直是空的

发表于 2026-09-11| 更新于 2026-09-11| 折腾记录
总字数: 2.7k| 阅读时长: 9分钟| 浏览量: —

这几天都在改左下角那个小人。原本只想让她换皮肤，后来接上了聊天，还让她能回答站里写过什么。功能做完那天，后台的聊天记录却一直是空的；最后发现数据早就存进去了，是后台页面压根没把它们画出来。

换皮肤，第一次点了没反应

小人是用 hexo-helper-live2d 渲染的，_config.yml 里只能写一个模型包。想加“点一下换一套”的功能，我先翻了引擎的源码，看到这么一段：

var t = document.getElementById(r.config.name.div);
null !== t && document.body.removeChild(t);
var i = document.createElement("div");

它每次初始化都会先把旧容器删掉再建新的。既然这样，那我再调一次 L2Dwidget.init({ model: { jsonPath: 新路径 } }) 不就换好了吗。

写完，点了一下，没反应。

不是报错，是什么都没发生：localStorage 里选择变了，皮肤列表里的选中态也变了，模型纹丝不动。

翻回源码找原因，在 configApplyer 那儿看到它合并配置的写法：

// merge(内部配置, 新配置, 默认值)
null == c ? n[o] = i : (两边都是对象) && merge(c, i)

意思是：目标里已经有值的时候，只有两边都是对象才会递归往下合，其它情况直接忽略新值。config.model.jsonPath 第一次 init 之后已经是个字符串了，所以我第二次传进去的字符串被丢掉了，theRealInit 拿着老路径又建了一遍容器。

那次白折腾了一轮。后来看 Widget 的构造函数时找到了办法：

this.eventHandlers = {}
this.config = u.config

L2Dwidget.config 就是 configApplyer 往里合并的那个对象本体。所以绕过 merge，直接改它：

window.L2Dwidget.config.model.jsonPath = 新路径
window.L2Dwidget.init(原来那份配置)

这样 merge 覆盖不了我刚写进去的值，容器重建时就按新路径来了。连着换两只试过，不会叠出来两个小人，页面也不跳。

顺手还做了一件事：访客上次选的皮肤，要第一次初始化就生效。不然每次进站都先下一套默认的（小春 500KB，静香 2.6MB），白花流量。插件那段 L2Dwidget.init({...}) 是页面里的内联脚本，而主题的 inject.bottom 正好画在它前面，所以我能在它之前把 window.L2Dwidget 的赋值拦下来，把选中皮肤的路径塞进第一次 init。

加新皮肤只要一条命令，npm i live2d-widget-model-xxx 然后重新构建，前端代码不用动。

聊天接在 Worker 后面

想让她能对话，得接个模型，我用的 DeepSeek。

这里有个绕不过去的事：博客是纯静态站，页面上的一切访客都看得到。把 API key 写在 JS 里，等于把自己的 key 和账单一起公开，谁都能拿去刷。所以走的是已有的 Cloudflare Worker 代理：浏览器只跟我的 Worker 说话，key 存在 Worker 的密钥里，前端拿不到。

限流一起做了。同一个 IP 每分钟 4 句、每天 40 句，另外有一个全站每天 300 句的总闸。最后这道闸是防着“被人换 IP 刷”的：单看每个 IP 都合规，加起来能把账单刷起来。

人设写在 Worker 的配置里，我写的是“说话像在群里闲聊，短句口语，别写成说明书”。有上限之后，一天 300 条封顶，按这个价格算是几分钱的事，但上限本身必须存在。

让她知道站里写过什么

一开始她什么都不知道。我问她“这个博客都写了哪些文章”，她的回答是：

这个我真说不准，我记不住站里每篇标题😂 你直接去首页翻翻分类和归档呗。

所以构建的时候多生成了一份文件，/ai-knowledge.json：站点信息，加上每篇文章的标题、日期、标签、链接、摘要，还有正文的前 2200 字。现在六篇一共 11KB。

Worker 在聊天之前先把这个文件拉下来（边缘缓存 1 小时），然后按提问里的关键词挑最相关的两三篇全文，和文章清单一起拼进 system prompt。

同一句话再问一次：

六篇，数得过来：《关于本站》《添加侧边栏电子钟》，还有最近几篇折腾记录——《源码丢了又找回来了》《留言板终于能留言了》《底图、封面，还有一个转圈的 bug》《两个新按钮，和它们带来的三个 bug》。想看哪篇说一声～

问“总结一下最新那篇”，它能把那篇讲的三件事说清楚，还带上了链接。这块比我想象中好用。

聊天记录存下来了

聊天的每条消息都落库了：正文、IP、UA、在哪个页面发起、会话 id，还有昵称。

昵称是和评论共用的：访客在评论区填过名字，聊天时前端就把那份名字一起发过来。要是他中途改了名，后台会把两个名字都列出来，标成“曾用名”。

这个是拿 IP 的哈希去两张表里一起查的（聊天表和评论表用的是同一个盐，哈希可以直接比），所以哪怕他只评论过、还没聊过天，第一次来聊天后台也能认出他换过名字。

前端聊天框上加了「清空」：清掉本地历史，同时换一个新的会话 id。换 id 是为了后台统计时能把“清空前后”分成两段，不然新对话会混进旧会话里。

数据在，后台却一片空

功能做完的当天晚上，有人说后台的「聊天记录」一直是空的。

先怀疑数据。 直接查库：

总数 14，带 path 的 10，会话数 6，最后一条 2026-09-11 20:28:38

朋友那条在最上面（IP 和我的不一样，来自 /comments/）。数据都在。

再怀疑接口。 不带口令请求一下，返回 {"ok":false,"error":"口令不对"}，说明接口是活的。

数据和接口都没问题，那就只剩页面。我写了个脚本，用无头浏览器真的打开后台点了一遍：

ReferenceError: loadChatSessions is not defined
    at switchTab (…/admin:72:13)

点「聊天记录」页签只是抛了这个错，所以列表一直停在初始那句「点上面的「聊天记录」标签加载」。看起来就是“空的”。

原因是那段聊天脚本的末尾少写了一个 </script>。整段 5000 多字的脚本被当成未闭合的 <script> 内容，浏览器压根不执行它，函数自然不存在。

补上那个标签，我以为完事了。

结果接着测渲染，又炸出来一个：

ReferenceError: i is not defined
    at shortUa (…/admin:273:20)

shortUa 是列表里显示“Chrome · Windows”那个函数，它里面写的是：

const br = /Edg\//i.test(s) ? 'Edge' : ...

但这一大段 JS 是放在 Worker 的模板字面量里的，而模板字面量会把 \/ 求值成 /。所以真正发到浏览器的代码变成了 /Edg//i.test(s)，被解析成”/Edg/ 除以 i.test(s)“，i 当然不存在。

改成用 includes 判断，不用正则，绕开转义。

之前后端的 127 项测试全绿，我才一直往数据库和接口那边找。后来翻了测试清单才发现，没有一项真的打开后台页面。接口能返回数据，页面还是可能什么都显示不出来。

所以补了一个 test:admin，做三件事：

  1. 把页面拼出来做静态检查：<script> 标签配不配对、每段脚本能不能被解析、有没有会被模板字面量吃掉的单个反斜杠
  2. 无头浏览器真的打开页面点一遍，确认脚本确实在跑、控制台没报错
  3. 用 CDP 把接口响应伪造掉，只测“拿到数据之后能不能正确渲染”（这段代码以前从来没被测过）

我还特意验证了这个测试真的能抓住原来的 bug：把修复撤掉，它立刻挂 11 项。

另外那天还学到一条：别用 PowerShell 对源码做字符串替换。我这么干过一次，把注释和 const ADMIN_CHAT_JS 挤到了同一行，整行变成注释、那段脚本直接不输出，还是靠语法检查才发现。

这几天顺手改的

手机端。用无头浏览器量了四个机型五个页面，问题都挺具体：正文 14px 偏小、汉堡按钮 29×38 手指点不准、评论输入框 14px（iOS 上一聚焦就自动放大整个页面）、首页卡片左右只剩 5px 贴边。挨个改了，另外加了图片灯箱（点正文图片全屏看），抽屉和灯箱打开时锁住背景滚动。

交接给帮忙运营的人。他只用写文章，所以我写了 README 和六个双击就走的 .bat：首次安装、新建文章、本地预览、一键发布、拉取更新、检查环境，外加一份分类的命令表。一键发布会自己构建、提交、推送（失败自动重试）、等线上更新，最后把浏览器打开给你看。

顺手发现这个工程里根本没装 hexo-server。原始备份的 package.json 里有，我重做的时候漏了，而 hexo generate 用不到它，所以一直没暴露。表现还挺隐蔽：npm run server 会打印一屏帮助然后以退出码 0 退出，看起来像正常结束。也就是说 README 里那条“本地预览”从来没生效过。

备份脚本。源码有 git 管着，但 bg-inbox/ 那 500MB 素材和一份 77MB 的原始源码压缩包不在版本库里，所以写了个双击打包的。用 Windows 自带的 tar 打 zip，580MB 只要 10 秒。

第一版打包出来中文文件名全是乱码，2-�½�����.bat 这样。查下来是 tar 默认按系统本地编码写文件名，而且不打 UTF-8 标志位，解压的工具看到没有标志位就按自己的默认编码猜。加一个选项就好：

tar -a -c -f backup.zip --options hdrcharset=UTF-8 .

顺带记一个教训：别用 tar -tf 去检查中文名。它打印的时候会按本地编码转一遍，控制台里照样是乱码，我就是被这个骗过去一次，以为文件里是好的。

后台终于能看到记录时，我又点了一遍「聊天记录」页签，才放心把这件事写下来。以后这张页面改了，光跑接口测试已经不能让我安心；得真的打开它、点进去看看。
