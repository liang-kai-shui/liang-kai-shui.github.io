宿舍网折腾记：能修的，和修不了的

发表于2026-09-20|更新于2026-09-20|折腾记录
|总字数:3.3k|阅读时长:10分钟|浏览量:

在宿舍住的这几天，网络问题一直是日常里最烦的一类：说它坏吧，能上；说它好吧，随机转圈、随机掉线、游戏连不上。

折腾久了慢慢有个判断标准：先分清哪一段是自己的责任范围。 出口带宽、认证方式、限速策略都在上游，学生手里一个都改不了；能改的只有从墙上那个网口到自己设备这一段。这篇只写这一段里真正有用的东西。认证、计费、出口那些在上游，不在本文范围内。

顺序大概是按”改完能立刻感觉到”排的。

一、每天手动登录这件事

校园网是门户（captive portal）认证：没登录之前，你发出去的一切请求都会被劫持到一个登录页。

这事最烦的不是登录本身，是掉了之后不会自己回来。晚上挂个下载，早上起来发现半夜就断了。

想自动化，得先看清楚登录到底做了什么。打开浏览器的开发者工具，在 Network 里勾上 Preserve log，然后手动登录一次，看那几个请求：

  • 一般是先 GET 登录页，从 HTML 里或者 Set-Cookie 里拿一个 token / 时间戳
  • 然后 POST 用户名密码（有的还带个 wlanacname、nasip 之类的参数，是接入设备标识）
  • 成功之后 302 跳回原页面，同时下发一个 session cookie

看清楚之后用 curl 复刻一遍就行。重点是三件事：带上那个 token、带上 Referer、带上 UA，少一个都可能被拒。

登录脚本本身十几行，真正值得花心思的是怎么判断”现在到底通不通”。

这里有个现成的办法：不要用 ping（校园网经常禁 ICMP，通不通都说明不了问题），用操作系统判断”有没有被劫持”的那套探测地址：

系统 探测地址 通了是什么样
Android connectivitycheck.gstatic.com/generate_204 HTTP 204、没有 body
苹果 captive.apple.com/hotspot-detect.html 返回一段固定的 HTML
Windows www.msftconnecttest.com/connecttest.txt 返回 Microsoft Connect Test
小米 connect.rom.miui.com/generate_204 HTTP 204

我自己的判断逻辑就是这个：204 才算通，其它一律当作掉线，重新登录一次。 比 ping 可靠得多，也比”能不能打开百度”稳定。

几个坑：

  • 密码别写死在脚本里。单独放一个 chmod 600 的文件里，或者用环境变量。这东西一旦跟着 dotfiles 传到 GitHub 上，改密码都来不及。
  • 别写死循环死重试。学校那边可能有”连续失败多少次锁账号”的策略，我见过同学把账号试锁了。间隔五分钟、失败三次就停手并通知我，比每秒钟重试安全。
  • 登录接口会变。学校升级系统那次我的脚本失效了两天，靠的是没用 -s 静默（保留报错）才看出来。所以脚本失败时一定要留下错误输出。
  • 有验证码就别硬来了。我遇到过的某套系统加了图形验证码，那种情况下手点比写脚本省事。

做成开机自启（OpenWrt 上丢一个 init 脚本），再配个 cron 每五分钟跑一次探测，掉线问题基本就消失了。

二、MTU 黑洞：最像”网络坏了”的一个坑

这个值得单独写一节，因为它的症状非常迷惑人：

  • 普通 HTTP 页面能打开
  • HTTPS 网站转圈打不开（或者要刷新好几次才开）
  • 小文件能下，大文件传一半卡死
  • ping 通，甚至很稳定

我第一次遇到的时候以为是 DNS 污染，换了三个 DNS 也没用；后来以为路由器坏了，换了一台还是一样。

真正的原因是路径 MTU 比 1500 小，而中间某台设备把 ICMP 的”包太大，请分片”这个回应给丢了。于是发出去的 1500 字节大包被静默扔掉，小包（比如握手的 SYN、DNS 查询）畅通。表现出来就是”能连上，但传不了数据”。

排查很简单，用不分片的 ping 一点点试：

能通就是 1500；报”需要分片但设置了 DF 标志”，就把 1472 往下降（降到 1452、1442、1400 都常见），找到一个能通的最大值，加上 28 就是这条路径的真实 MTU。

我这边最后落在 1400。改完之后 HTTPS 不再转了，大文件传输也正常了。那个”网络时好时坏”的体感，九成是这个。

怎么改：

  • 单台设备：Linux 上 ip link set dev eth0 mtu 1400（要持久化得写进网络配置）；Windows 在网卡属性里改
  • 路由器上改 WAN 口 MTU（OpenWrt 是 network 配置里的 mtu 和 mtu6）
  • 更省事的办法是在路由器上做 MSS clamping，让 TCP 握手时就把双方的最大段长压到路径 MTU 以下，客户端不用动：

（OpenWrt 新版用 nftables，等价写法是 tcp option maxseg size set rt mtu。）

提醒：改 MTU 解决的是”卡死”，不解决”慢”。带宽不够的时候调 MTU 一点用都没有，别指望它提速。

三、IPv6：学校给了，但先看清楚规定

多数校园网现在是双栈，而且给的是真的公网 IPv6，不是 NAT 后面的内网地址。我那会儿路由器 WAN6 上拿到的是 /64 的段。

先说要紧的：用之前确认学校对 IPv6 的计费规定。 有的学校 IPv6 不计流量（教育网出口常这样），有的照算，还有的是校内 V6 资源免费、出去收费。默认它免费是个挺危险的习惯，我见过被扣了钱才发现的同学。

好处是实打实的：有了公网 IPv6，从外面连回宿舍的电脑不需要任何内网穿透。 手机热点下直接 ssh 回宿舍，延迟比走中继低一个数量级。这是 IPv6 对我最大的价值，比”访问 V6 资源”有用得多。

但代价也要说清楚：IPv6 没有 NAT 挡在前面。 IPv4 时代家里一堆设备暴露在公网上没人扫，是因为 NAT 天然把它们藏起来了；V6 里每台设备都是真·公网地址，开了端口就是真开着。我的做法是：

  • 默认全 drop，只放需要的端口（而且不放在常用端口上）
  • SSH 只允许密钥登录，关掉密码认证
  • 定期看一眼 ip6tables -L 有没有手滑加的规则

另外 IPv6 出口不一定健康。我遇到过：能 ping 通外面的 V6 地址，但 TCP 建不起来。原因在学校的 V6 出口上，客户端这边没有任何办法。所以别把 IPv6 当成唯一的路径，双栈并存、让系统自动选，比强行只走 V6 稳。

四、DNS：学校那台别全扔

很多人一遇到网络慢就先换 DNS，这步经常白做，还容易把校内资源搞坏。

学校 DNS 有一个别人替代不了的作用：解析校内域名。图书馆的电子资源、教务系统、内网的各种服务，只有校内 DNS 才知道它们指到哪。你把 DNS 全换成公共 DNS 之后，第一个挂掉的就是图书馆。

我的做法是分流：

  • 校内域名（比如 *.edu.cn 里属于自己学校的那些、还有学校自己的域名）走学校 DNS
  • 其它走加密 DNS，OpenWrt 上用 https-dns-proxy 或者 dnsmasq 转发 DoH
  • 先在 dnsmasq 里把校内域名指到学校 DNS，其余的走 DoH

在我这边两者差别很小，都在 10ms 上下。也就是说换 DNS 对”网页打开速度”的改善基本感知不到，真正的瓶颈在出口带宽。老老实实做分流的收益（校内资源能开）比换 DNS 的收益大。

五、路由器：贵没用，位置有用

宿舍路由器不需要买贵的。三五百块能刷 OpenWrt 的就够，贵的那些附加功能（游戏加速、双频合一的高级调度）在这个场景里基本用不上，而能刷机意味着你能自己控制 MTU、DNS、防火墙、DDNS 这些真正有用的东西。

几个实测出来的结论：

  • 能插网线就插网线。 同一个网络，有线打游戏的延迟比 WiFi 稳得多，这个差别比换任何设备都大。
  • 5GHz 穿墙很差，隔一堵墙就掉一大截。路由器别塞在铁柜子里、别压在书堆下面，挪到开阔位置就能明显改善。
  • 2.4GHz 是公共频谱，宿舍楼里几十个热点叠在一起。用 WiFi 分析工具看哪个信道最空，在 1 / 6 / 11 里挑一个换过去，能躲开一点，但赢不了，这是物理条件决定的。
  • 路由器 WAN 口的 MAC 地址学校那边可能是记着的。换设备的时候留意一下学校有没有绑定，别莫名奇妙上不了网还以为路由器坏了。

六、从外面连回宿舍

要出门又想用宿舍的电脑、翻下载进度、访问 NAS，内网穿透是刚需。

我用 Tailscale（底层是 WireGuard）：两端各装一个，不用公网 IP、不用配端口映射，登录同一个账号就组起来了。

体感上的重点是打洞成不成功：

  • 双方 NAT 都不太严格的时候能直连，速度基本跑满自己带宽，延迟跟局域网差不多
  • 打洞失败就走官方中继，能用但明显慢，而且延迟高

想确认走的是哪条路，tailscale status 里能看到 direct 还是 relay。如果一直是 relay，值得查一下路由器上的 UPnP / NAT 类型。

如果有公网 IPv6（上一节那种），直连更快，不用穿透，直接连 V6 地址就行。代价是要把防火墙配好。

七、游戏连不上：这条基本没得修

校园网是个大内网，你拿到的 IPv4 是学校内网的地址，没有公网 IPv4、也没有端口映射的权限。这对联机游戏的影响是硬伤：

  • 你不能做主机，别人连不进你
  • 一些平台会因为你 NAT 类型太严，干脆不让你进别人的房间

唯一有效的缓解是让双方处在同一个虚拟网段里：和朋友一起加入同一个 Tailscale 网络，你们之间就相当于局域网，联机走这条隧道。缺点是只有同样装了的人之间能用。

剩下的偏方（改 DNS、开 UPnP、调 MTU）在这一点上都无效，因为问题出在”你在 NAT 后面、而路由器不归你管”。这是典型的上游问题，客户端无能为力。

八、哪些别浪费时间

按我这几年的经验，下面这些是心理安慰大于实际效果：

  • 换 DNS 提速：解析耗时本来就只有十几毫秒，瓶颈在出口带宽
  • 调 MTU 提速：它只解决”卡死”，不解决”慢”
  • 想让宿舍 WiFi 打赢整栋楼：2.4G 是公共频谱，只能避开干扰源，不能压制它
  • 反复重启路由器：能好一会儿，但如果是上游的问题，它还会回来
  • 给宿舍网测速然后怀疑自己路由器：先用有线直连测一遍，很多”路由器不行”最后是网口本身就不行

反过来，按收益从高到低排，值得做的就这四件：

  1. 能走有线就走有线（延迟和稳定性的差别最大）
  2. 把 MTU 调对（解决”随机打不开网页”这种最烦的症状）
  3. 把登录自动化（解决”半夜掉线”）
  4. 调一次信道和路由器位置（一次性工作，收益持续）

最后

宿舍网最容易让人上头的地方，是它随机：今天好好的，明天转圈，你永远不知道是自己改了什么东西还是学校那边动了什么。

真正让这件事变清爽的，是先把”哪些归我管”分清楚。归自己管的就上面那几件，做完就是做完了，剩下的波动不用再怀疑是自己的问题。那是上游的事，认了就行。

至于出口带宽、认证方式、计费策略这些，本来就不在学生手里，改不了也不用惦记。
